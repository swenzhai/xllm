# T5QKV 007/017 性能整改方案

日期：2026-11-13。状态：方案已制定，尚未实施新的内核优化或完成新的NPU复测。

## 1. 目标与当前结论

解决007在审核复测中的绝对耗时超限，同时回归同几何尺寸的017和其余8个性能case。正式上限保持007≤75µs、017≤77µs；精度、输出独立存储、输入不变、当前stream、零显式workspace等合同保持不变。

内部调优目标是把007典型耗时压到约68–70µs，并使独立进程复测的最慢批次留出数微秒余量。这是优化目标，不是已证明的收益，也不替代原验收阈值。一次74.9µs或某种allocator下偶然通过，不作为整改完成依据。

审核员反馈由用户转述，没有附带原始JSON/log、命令和环境指纹：

| 口径 | 007耗时(µs) | 超限情况 |
| --- | --- | --- |
| 默认allocator | 75.50、80.55 | 2/2超限，最大超5.55µs |
| page_size:1g | 71.51、75.41、74.82、75.78 | 2/4超限，最大超0.78µs |

反馈中的“差距＜1µs”只适用于上述1g超限值。约0.32的同机当前/基线比值能证明收益，不能抵消绝对上限失败。精度35/35、内存10/10、工程206/206被审核员报告为通过；“其余8例”不能确定017的具体情况，因此017必须一起复测。

代码参照：实现8ea9affaf131b22c8fb786b79da5968ce6724744，旧交付83d54c8，反馈状态更新247036e。旧五批通过作为历史数据保留，不能继续支持当前可验收结论。

## 2. 对问题的判断

当前还不能判定唯一根因。已有证据支持优先检查以下三类问题：

1. **缓存和地址布局敏感性。** 当前大shape正常缓存的逻辑工作集为188.15625MiB，接近此前记录的名义192MiB L2容量；有效容量、组相联冲突、框架数据和物理页布局可能影响驻留。软件预算不能证明实际命中。旧诊断中同一缓存策略出现明显不同的读命中事件数，说明缓存历史值得优先验证，但这些旧诊断不是当前失败批次的根因证明。
2. **搬运流水仍有开销。** 当前每head三个历史tile，尾块融合当前token。每核需要发起多个DMA并同步事件，存在标量地址计算、缓存类别切换和末尾排空成本。能否再省几微秒须由当前版本的A3 profiling决定。
3. **端到端API或运行环境波动。** 正式计时包含新输出分配、两阶段调用和提交到完成。CPU调度、host queue、allocator或其他负载可能改变结果；不能把全部变化归咎于kernel，也不能仅以“噪声”否定审核失败。

默认allocator最差80.55µs说明只节省0.5µs不够；方案同时追求降低固定开销与降低运行间波动。

## 3. 第一阶段：先建立可复现对照

### 3.1 恢复目标环境

必须使用910C/Atlas A3，核实实际SoC、可见设备、CANN、driver、torch/torch_npu及CPU环境。此前用户接受的Ubuntu/driver开发环境差异仍披露。VS Code当前服务器openlibing-DevEnv-464458实测为910B4；用户确认A3暂时没有资源，当前不具备正式性能闭环条件。

A3恢复后在独立任务目录构建，先记录源码commit、编译选项、包和加载库SHA；不复用来源不明的旧库，不与其他任务同时占用NPU进行性能实验。

### 3.2 复现原版本

- 保持原官方生成器、CPU golden、benchmark和性能检查器字节不变；仍是50次预热、200次×5轮，每批取5个轮均墙钟耗时的中位数。每次调用分配新输出。
- 首先对原版本进行默认allocator与page_size:1g各3个新进程的全10项计时，配置执行顺序交替，保留全部成功、失败及环境记录。不因先跑的配置更快就固定有利顺序。
- 两种allocator分开统计；page_size:1g必须在导入torch前设置。整改主方向优先覆盖默认allocator，1g作为独立补充口径。除非验收方另有明确配置要求，不能只提交1g最快数据替代默认结果。
- 若原版本暂时全通过，也不能认定问题消失。接续独立进程复测并保留结果，以检验已知的间歇超限；不丢弃慢批次、不合并不同批次挑选五轮。
- 常规的完整10项benchmark是正式数据。单独筛选007/017、改变顺序或冷缓存实验只能用于诊断，必须明确标记，不能替代原公开协议。

### 3.3 拆分耗时证据

对正常和慢批次对应的运行条件，另开诊断进程采集CANN kernel时长及可用MTE2/MTE3、标量和L2原始计数，保留原始CSV。profiling与最终无插桩性能分开。

| 观测 | 后续优先动作 |
| --- | --- |
| kernel时长随API耗时一起升高，L2读事件也有差异 | 优先缓存准入和读写调度 |
| kernel时长稳定，API耗时变化明显 | 优先框架/allocator/host queue归因 |
| kernel标量或事件间隙明显，MTE仍有空隙 | 验证几何尺寸专用调度 |
| 有其他进程或明显系统干扰 | 保留原失败记录，记录环境后重新独立测量，不自行删除“异常值” |

设备event包含提交间隙，不直接称为纯kernel时间。不同计时范围的中位数相减不能精确还原CPU开销；host与device归因使用实际trace和可比计时范围。

## 4. 第二阶段：候选优化按优先级推进

### P1：缩小正常缓存工作集，验证稳定性收益

当前007/017几何尺寸B=16、H=16、L=2048、D=64；T=47104、C=3、P=48，正常Value输入前缀240行。保留现有手工双槽流水、Key输入/输出hint、Value输出bypass及tail融合，只改变Value输入的正常缓存准入，先做两个单变量候选：

| 候选 | 正常Value前缀 | 预计正常逻辑工作集 | 相对当前额外旁路读取的数据 |
| --- | ---: | ---: | ---: |
| 对照 | 240行 | 188.15625MiB | 0 |
| C1 | 224行 | 184.15625MiB | 每次4MiB |
| C2 | 208行 | 180.15625MiB | 每次8MiB |

每16行对应48个历史tile，能保持三个缓存类别的整核任务分配。候选的收益假设是为缓存替换留空间，代价是增加旁路读取；不能假定前缀越小越快。

实现应使用共享策略helper和可解释的字节预算/分组规则，不根据Case ID、dtype数据内容或计时轮次选择。保留合法shape通用路径，对改变策略的shape回归边界、storage_offset和两入口精度。

旧的读平衡、前缀缩减、cache hint及分配器试验必须按“当时流水+allocator+形状+源码”索引。224行在旧组合失败不证明本组合必败，同样不能将旧组合的偶然通过当成新候选收益。新实验与旧实验的差异必须明确，避免无差别扫描172–192MiB预算。

### P2：在profile支持时降低固定搬运调度开销

只有P1不足以达到稳定余量且profile支持时再做，避免同时改多个因素：

- 为明确的合法大几何尺寸提供编译期专用路径，使C=3、headNum=16、headDim=64、行长和tile偏移成为常量，减少循环内除法、取余、重复分支和动态描述构造；仍以输入元数据派发，适用于007/017同形状的两dtype，不读取case名。
- 保持两个92KiB槽及独立MTE事件所有权，优先消除重复游标状态/描述符计算；从生成代码和profile核实是否实际减少指令。现有代码已经采用增量游标，不能将“改为游标”再作为新增优化。
- 若发现末尾Q复制或phase排空构成可见尾部开销，再比较一次调度重排；必须证明所有输出区间唯一writer，且不存在输入/输出数据依赖。已有当前token尾融合不再重复设计。
- 对任一事件/预取顺序修改，检查槽复用前等待写完成、读就绪后才写回、所有flag成对及ID最终释放。不能为了少一次等待破坏同步。

不优先尝试扩大UB、盲增第三槽、全量缓存/bypass、循环分核、补齐大块输出分配等已多次波动或退化的方向。若profile提出新证据，再以独立候选重开，不能凭猜测恢复。

### P3：只在证据证明host开销占比显著时优化框架

复查固定元数据构造、校验、动态库解析、两阶段API和OpCommand排队中能否去掉重复工作。动态库符号当前已经首次加载后复用，不把这一点再当作新收益。

禁止缓存输出、复用跨调用executor、返回输入别名、跳过必要输入校验或改变异步/recordStream语义。默认allocator是框架配置，不能在算子内强行改变全局allocator来隐藏性能问题。

## 5. 实验预算与淘汰机制

首个A3资源窗口建议控制在约4小时，最多6个内核候选，作为首轮研究预算，实际构建/采样耗时另行记录。顺序为原版本复现→C1/C2→根据profile最多3个定向候选→最优候选扩大复测。达到预算仍未闭合时保留现状并重新归因，不通过增加无方向候选数量掩盖失败。

每候选先做位级精度/地址覆盖检查，再做默认与1g各3个新进程的原完整10项benchmark；对照与候选交错运行。观察每批原统计量、最慢批次、跨度和失败批次计数；跨批中位数、P95等仅用于诊断，不能覆盖单批官方失败。样本少时不以P95等尾部分位数宣称可靠性。

淘汰条件：错误/输入修改/输出别名/内存回收异常立即淘汰；收益只在一个allocator或一个进程出现、其他case明显退化、最慢批次仍反复越界的候选不得升级为交付版。候选退出时保留源码快照、构建/安装产物hash及全部原记录。

## 6. 最终复测与交付门槛

候选选择和最终确认分开，最终确认使用此前未用于选优的新进程批次：

1. 默认allocator做10批、page_size:1g另做10批，每批原完整10项、50/200/5协议。每一批按原checker独立判断，要求007≤75µs、017≤77µs且其余8项均通过。若验收方明确只验一个配置，以其配置作为正式口径，另一个配置仍据实披露。
2. 拟正式提交配置下完成官方精度35、工程206、内存10，以及cache/tail/hot geometry、队列/生命周期、CPU映射、两入口交叉验证和独立C++样例；默认和1g均声称支持时，各自补齐对应完整回归证据。
3. 同NPU、同输入、同allocator重新测量独立合格的views_concat_q_copy基线，F/E仍单列，不代替绝对checker。
4. 10批无失败只是本次有限复测门槛，不代表统计上保证永不超限；在报告同时披露最慢批次及余量。若007仍贴着75µs，应继续优化或诚实报告稳定性风险。
5. 冻结源码及加载库前后指纹，保存真实stdout/stderr、所有五轮样本、环境及输入hash；取得与最终版本一致的真实截图。
6. 通过后从统一ledger更新报告；保持三份XLSX原格式，更新相应单元格、截图和指纹。原失败证据保留。重新生成四类目录的单ZIP，核对文件集合、SHA和仓库副本，按既有授权commit/push。

任何最终批次超限都不能写“已全部达标”。当前旧交付包保持历史属性，只有整改复测通过后才生成新的可提交版本。
